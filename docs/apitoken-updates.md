# APIToken 合并版更新

本分支保存站点定制功能，并以 `ranxi2001/sub2api` 的正式发布版为上游。首次接入的官方基础为 **v2.23.0**，合并版为 **v2.23.0-apitoken.8**；后续版本以仓库 Releases 为准。官方原版二进制不包含本站定制功能，不能直接替换合并版。

## 后续更新方式

1. 在自己的 GitHub 发布仓库里打开 **Actions → APIToken combined release → Run workflow**，选择保存定制代码的分支。
2. 官方标签留空时获取最新正式版，也可指定 `vX.Y.Z`。勾选 `publish` 才会在通过验证后发布；默认只生成可下载的测试产物。
3. 流程合并官方正式版，检查已执行的数据库迁移文件未被改写，验证签名插件、USDT 真假币/金额防重、分组修复及前端，然后构建合并版。应用代码冲突或检查失败会停止，不推送源码、不发布、不更改线上服务。
4. 发布成功后，在网站版本菜单点“刷新 → 立即更新 → 立即重启”。主程序从自己的合并版仓库下载，无需再手动上传主程序。数据库、账号、订单、密钥和插件配置沿用原目录。

流程由手动运行触发，没有定时任务。未来官方改动若与定制功能冲突，需要修复冲突并验证后再发布，不能保证所有未来版本都能无人处理地合并。

## 升级到 .9：独立 USDT 计价

先备份数据库、配置与密钥，并暂停 USDT 插件。升级主程序到 `.9` 后，安装 USDT 插件 **1.1.0**，在配置中设置独立手续费和 USDT/CNY 汇率，再测试连接并启用。升级不会重新计算旧订单；新插件不支持旧宿主。客服插件继续使用 1.0.6。

## 首次接入

- 使用自己控制的 **公开 GitHub 发布仓库**，建议保留独立的 `apitoken` 分支。当前下载器使用 GitHub 公开 release 资产地址；私有仓库资产不能仅凭 `UPDATE_GITHUB_TOKEN` 下载。
- 将完整合并版源码和 `extensions/releases/` 中两个签名插件包保存到该分支。不要上传服务端配置、用户数据库、账号文本或签名私钥。
- 保留 `deploy/apitoken-upstream.json`、`deploy/apitoken-plugins.lock.json` 和 Git 历史。只有基于正式版的完整历史可进入自动合并流程。
- GitHub Actions 需允许工作流写入仓库内容。现有上游 Release 工作流在本分支已限制到上游仓库，合并版使用独立流程，避免两套发布流程互相覆盖。
- `.github/workflows/` 由合并版维护，自动合并时保留运行前的完整目录，不引入官方对工作流的新增、修改或删除。这样保留发布保护规则，也无需提供能修改工作流的额外令牌。官方应用代码照常合并；需要采用官方 CI 改动时，单独审查并提交工作流更新。
- 工作流不需要插件签名私钥：它复用已经签名且锁定 SHA-256 的发布包，并在候选主程序上进行真实安装、启停和重启恢复测试。插件源码或协议改变时，锁定校验会停止发布，需要重新构建、签名和测试插件后更新锁文件。
- 第一次由 `.7` 迁移到 `.8`，先备份数据库、主程序、`config.yaml` 与 `data/secrets`。先在 `.7` 的插件管理中升级 **USDT 1.0.2**、**客服 1.0.6**，保留配置并重新启用；它们仍兼容 `.7`。再安装绑定正确仓库的 `.8` 主程序。之后同一协议下的主程序升级继续使用这两个插件。
- 合并版构建会内置正确的更新仓库；也可在 systemd 的服务环境中设置 `APITOKEN_UPDATE_REPOSITORY=你的用户名/你的仓库名` 后重启。未配置、填写官方仓库或配置无效时，自动更新保持关闭并给出明确提示。

普通用户不会看到更新管理入口。后台显示当前合并版版本、官方基础版本、更新来源及检查状态。

## 更新与回退边界

合并版更新同时验证：仓库、正式 release、`vX.Y.Z-apitoken.N` 标签、平台文件名、`checksums.txt`、包内来源信息与二进制 SHA-256。缓存按仓库和渠道隔离，网络检查失败不允许用旧缓存执行替换。`.9` 和 `.10` 按数字比较。

在线回退仅列出同一官方基础版本下、支持新发布契约的最近三个合并版，最低为 `.9`；不提供原版官方二进制、不同官方基础版本或未经验证的本地旧备份回退。数据库不做降级。涉及新数据库结构的未来改动，应提高最低兼容版本或更新发布契约，不能只改版本号。

390 号迁移支持订单独立保存可变汇率；`.8` 及更早宿主仍按固定汇率处理，不能处理新版发票。`.9` 起仅允许回退到支持独立计价的版本。388/389/390 号迁移文件均固定校验，不改写已执行迁移。

## 本地验证和构建

使用项目 `backend/go.mod` 声明的 Go 版本、Node.js 22、pnpm 9、Python 3.9+ 和专用测试 PostgreSQL。测试数据库必须与线上隔离。

```sh
pnpm --dir frontend install --frozen-lockfile
python3 scripts/apitoken/release.py verify
USDT_TEST_POSTGRES_DSN='postgres://测试用户:测试密码@127.0.0.1:5432/测试库?sslmode=disable' \
  python3 scripts/apitoken/release.py test
python3 scripts/apitoken/release.py build --repository 你的用户名/你的仓库名
```

本流程构建线上使用的 `linux/amd64` 主程序。自动生成 `.tar.gz`、两份签名插件包、对应源码归档与 `checksums.txt`。发布前工作区必须干净，确保可下载源代码与二进制来自同一提交。构建脚本本身不上传、不部署。

升级过程继续使用原有后台操作锁、原子二进制替换和重启确认。每次生产升级前仍需完成数据库备份；自动更新不等同于自动创建数据库备份。
